1. VSIX パッケージング

VSIXユーザーインストールでは pkgdef が読まれない

VSIXInstaller.exe foo.vsix (管理者なし) で入れると拡張は「インストール済」になるが、 pkgdef による TextMate grammar 登録が効かず全機能が動かない。

VS 2022 は PkgDefSearchPath にユーザー拡張フォルダを含めない。 pkgdef で登録した grammar / editor mapping / language service は システム配置 (/admin) のときだけ読まれる。

VSIXInstaller.exe /admin /q foo.vsix (管理者コンソールから実行)。 開発ループ用に reinstall_admin.bat を同梱する。

VSIX/admin 時は manifest.json に全ファイルの SHA-256 必須

「Invalid VSIX package」でインストール失敗。manifest.json に listed されていないファイルが zip 内にあると落ちる。

VsixUtil.exe の auto-gen は不十分。手書きスクリプトで全 payload を列挙し { fileName: "/foo", sha256: "..." } 配列を作って manifest.json に書く必要がある。さらに catalog.json も マニフェスト 1.1 形式で必要。

build_vsix.ps1 を参照 — payload 配列 → SHA-256 → manifest.json/catalog.json 自動生成。

VSIXProductArchitecture は amd64 (x86 不可)

<ProductArchitecture>x86</ProductArchitecture> にすると NoApplicableSKUsException。

VS 2022 本体が 64-bit 化されたため、拡張側の宣言も amd64。

VSIXzip エントリは forward slash 必須

Windows の ZipFile.CreateFromDirectory が出す backslash パス (Grammars\nhsp.tmLanguage.json) だと VSIXInstaller が path を認識しない。
7z.exe a -tzip を使うか、ZipArchive.CreateEntry(string entryName, ...) で明示的に / 区切りのエントリ名を渡す。

VSIX[Content_Types].xml で全 payload 拡張子を宣言必須

「Invalid VSIX package」でインストール失敗。OPC の仕様で zip 内の各ファイル拡張子は [Content_Types].xml で MIME type にマップされていないといけない。 
<Types xmlns="http://schemas.openxmlformats.org/package/2006/content-types">
  <Default Extension="vsixmanifest" ContentType="text/xml" />
  <Default Extension="pkgdef"       ContentType="text/plain" />
  <Default Extension="json"         ContentType="application/json" />
  <Default Extension="dll"          ContentType="application/octet-stream" />
  <Default Extension="exe"          ContentType="application/octet-stream" />
  <Default Extension="config"       ContentType="text/xml" />
  <Default Extension="xml"          ContentType="text/xml" />
</Types>
payload に新しい拡張子を追加するたびに忘れず [Content_Types].xml も更新する。

VSIX同じ ID の既存拡張があると新規インストールできない

VSIXInstaller がエラーなしで silent fail、あるいは「このバージョンは既にインストール済み」と表示。
インストールの前に必ず uninstall。再インストールスクリプトにも組み込む: 
"%VSIXER%" /admin /q /u:IronHSP.NhspLanguage.5b3a8b62-3f6e-4f9e-a2bd-6e4a8c1e6b7e
"%VSIXER%" /admin /q "%VSIX%"
初回 uninstall 時は errorlevel=2002 が出るが 無視して続行して OK (= 「元々入ってなかった」)。

VSIXVS が起動中だと DLL lock で再インストールできない

開発ループで /admin で上書きインストールしたら「ファイルがロックされています」。

MEF component DLL は VS プロセスが掴みっぱなしなので、稼働中の VS 2022 を全て閉じてから reinstall する。 最低でも対象の VS インスタンスは落とす。

2. TextMate grammar の読み込み

VSIX$schema 行で grammar が reject される

"$schema": "..." を含む .tmLanguage.json を pkgdef 経由で登録しても、 VS 2022 の TextMate parser は無言で reject する。シンタックスハイライトが一切効かない。
$schema 行を grammar JSON から削除する。VS Code 側は許容するので、 その設定は .vscode/settings.json か別の schema 指定手段に逃がす。

3. MEF ContentType ルーティング

MEF[BaseDefinition("code")] で TextMate が無効化される

ILanguageClient を MEF export するために ContentTypeDefinition も export すると、TextMate の色付けが効かなくなる。

[BaseDefinition("code")] は .xxx ファイルを「標準のテキストエディタ」に紐付けてしまい、 TextMate grammar の経路をバイパスする。 

[Export]
[Name(ContentTypeName)]
[BaseDefinition(CodeRemoteContentDefinition.CodeRemoteContentTypeName)]
internal static ContentTypeDefinition NhspContentType;
CodeRemoteContentDefinition.CodeRemoteContentTypeName (MS VSSDK-Extensibility-Samples の LSP サンプルで使われている) が「LSP 向けだが TextMate 経路は残す」正解。

4. LSP (built-in VS 2022 client) の癖

LSPHover.contents の markdown body が消される

MarkupContent { kind: "markdown", value: "```xxx\nsignature\n```\n\nSummary\n@param ..." } を返すと、signature の code fence だけ表示されて summary 以降が無音で捨てられる。
Contents 型結果
MarkupContent { kind: "markdown" } 複数行先頭 code fence のみ表示、body 欠落
MarkedString[] (plain string 配列)全部表示 / markdown 未解釈 (**bold** が生で出る)
MarkedString[] 先頭 {language, value} + 以降 plain先頭 code block だけ色付き
MarkupContent { kind: "plaintext" }全文表示 / 色なし ← 現状の落としどころ

Microsoft.VisualStudio.LanguageServer.Client 17.x のレンダラ側の既知問題。 MS 公式 VSSDK sample ですら Hover は単一 "Mock Hover" 文字列しか返していない。

色付きが必要なら VS 2022 LSP 経路ではなく、IAsyncQuickInfoSource を MEF export して 自前で QuickInfo UI を構築する (Roslyn / PTVS の道)。本リポジトリでは plaintext で妥協。

4.5 LSP URI の Windows drive colon 問題

LSPfile:///j%3A/... を Uri.LocalPath が正しくデコードしない

VS Code で .xxx ファイルを開いた瞬間に「internal: 指定されたパスのフォーマットは サポートされていません」という diagnostic が 1:1 に出る (エディタ上は赤波線)。 デバッグ実行やコンパイルは通る。

VS Code は Windows パスを送るとき drive colon を URL-encode して file:///j%3A/HNWorks/foo.xxx の形にしてくる。.NET の new Uri(s).LocalPath は URL 解釈時点で drive 検出をやるため、 encode された %3A を後からデコードしても先頭の / が 残って /j:/HNWorks/foo.xxx という不正なパスになる。 これに Path.GetFullPath を掛けると NotSupportedException が飛ぶ。

URIUri.LocalPathPath.GetFullPath
file:///j:/fooj:\fooOK
file:///j%3A/foo/j:/fooNotSupported
file:///C:/fooC:\fooOK
file:///J%3A/foo/J:/fooNotSupported
private static string UriToPath(string uri) {
    if (string.IsNullOrEmpty(uri)) return null;
    try {
        var u = new Uri(uri);
        if (!u.IsFile) return null;
        string path = u.LocalPath;
        // file:///j%3A/foo → "\j:\foo"。leading separator を剥がす。
        if (path.Length >= 3 &&
            (path[0] == '\\' || path[0] == '/') &&
            char.IsLetter(path[1]) && path[2] == ':')
            path = path.Substring(1);
        return path;
    } catch { return null; }
}
VS Code / VS 2022 built-in LSP client 両方でこのパターン。テストは file:///j:/..., file:///C:/... も走らせて regression が出ないこと確認。

5. エディタ拡張 API の落とし穴

EditorIVsTextView から IVsCodeWindow に直接到達できない

ナビゲーションバー (IVsDropdownBarManager) を attach しようと vsView as IVsDropdownBarManager したら null。IOleServiceProvider 経由の QueryService(SVsCodeWindow) もぜんぶ失敗 (VS 2022 では vsView as IOleServiceProvider も null を返す)。
shell の document frame を列挙して、primary/secondary view が match する IVsCodeWindow を探す。これだけが通る道: 
var uiShell = Package.GetGlobalService(typeof(SVsUIShell)) as IVsUIShell;
uiShell.GetDocumentWindowEnum(out IEnumWindowFrames winEnum);
var frames = new IVsWindowFrame[1];
while (winEnum.Next(1, frames, out uint fetched) == VSConstants.S_OK && fetched == 1) {
    frames[0].GetProperty((int)__VSFPROPID.VSFPROPID_DocView, out object dv);
    var cw = dv as IVsCodeWindow;
    if (cw == null) continue;
    cw.GetPrimaryView(out var primary);
    cw.GetSecondaryView(out var secondary);
    if (primary == target || secondary == target)
        return cw as IVsDropdownBarManager;  // ← code window は両方実装している
}
実装: NhspTextViewCreationListener.FindCodeWindowByEnumeration

Editorナビゲーションバーは IVsDropdownBarClient 自前実装

LSP の textDocument/documentSymbol を VS 2022 が自動でナビゲーションバーに 繋いでくれる仕組みはない。Roslyn / PTVS は独自実装している。 単純な言語ならソース正規表現パースで十分。

IVsDropdownBarClient.GetComboAttributes の puEntryType は DROPDOWNENTRYTYPE enum だが VS SDK バージョンによって名前が揺れるので 0x1 (ENTRY_TEXT) を即値で渡すのが安全。FONTATTR enum も 同様に名前揺れがあるので pAttr = 0 (= FONTATTR_PLAIN) を即値で返す。

EditorENTRY_IMAGE を立てると画像リストが必須

puEntryType に ENTRY_IMAGE (0x4) を含めた場合、 phImgList が非 null (valid な HIMAGELIST) じゃないと描画失敗する。 画像なしでいいなら ENTRY_TEXT (0x1) のみにして phImgList = IntPtr.Zero、 GetEntryImage は呼ばれないように仕向ける。

MEFMicrosoft.VisualStudio.Editor NuGet が必須

IVsEditorAdaptersFactoryService.GetWpfTextView(vsView) のために Microsoft.VisualStudio.Editor への参照が必要だが、Shell.15.0 だけでは引っ張られない。
<PackageReference Include="Microsoft.VisualStudio.Editor" Version="17.0.491" PrivateAssets="all" /> を csproj に追加。IVsTextViewCreationListener で IVsTextView ↔ IWpfTextView 相互変換に必須。

6. デバッグ起動 (F5 / ツールバー ▶)

DebugLaunchDebugTargets4 の engine GUID を空にすると E_INVALIDARG

guidLaunchDebugEngine = Guid.Empty, dwDebugEngineCount = 0 で呼ぶと HRESULT 0x80070057 (E_INVALIDARG) を返して起動できない。
managed (CLR2/CLR4 両対応) engine GUID を明示する: 
static readonly Guid ManagedEngineGuid =
    new Guid("449EC4CC-30D2-4032-9256-EE18EB41B62B");

var info = new VsDebugTargetInfo4 {
    dlo = (uint)DEBUG_LAUNCH_OPERATION.DLO_CreateProcess,
    bstrExe = exe,
    bstrCurDir = Path.GetDirectoryName(exe),
    guidLaunchDebugEngine = ManagedEngineGuid,
    LaunchFlags = (uint)__VSDBGLAUNCHFLAGS.DBGLAUNCH_StopDebuggingOnEnd,
};
((IVsDebugger4)Package.GetGlobalService(typeof(SVsShellDebugger)))
    .LaunchDebugTargets4(1, new[] { info }, new VsDebugTargetProcessInfo[1]);

Debugツールバー ▶ は「startup item」がないと Debug.Start を発火しない

IVsRegisterPriorityCommandTarget で VSStd97CmdID.Start を intercept しても、 ツールバー ▶ をクリックすると「スタートアップ アイテムの選択」dropdown が出るだけ (そもそもコマンドが dispatch されない)。F5 キー / Debug メニュー / 右クリックは動く。
VS 2022 Open-Folder の ILaunchDebugTargetProvider / ILaunchConfigurationProvider を MEF export する。詳細は次セクション。これを付けると dropdown に 「現在のドキュメント (xxx.xxx)」が自動で出て ▶ も動くようになる。

Debugpriority target と Workspace provider の二重発火

ツールバー ▶ を 1 回クリックしたのに compile が 2 回走り、2 回目が ERROR_SHARING_VIOLATION (0x80070020) で失敗する (1 回目の exe を debugger が掴んでいるため)。

priority command target と Workspace LaunchDebugTarget の両方が Start を拾ってしまっている。

Workspace provider 1 本に絞る。F5 / ツールバー / Debug メニュー / 右クリック全経路が Workspace 経由で届くので、それ以外の command filter は削除して OK。 nhsp では NhspCommandFilter.cs と NhspGlobalCommandTarget.cs を commit a48e67bd で削除した。

7. Open-Folder / Workspace 拡張

Shell「現在のドキュメント」dropdown の正体

PTVS が .py で "Current Document (xxx.py)" を dropdown に出している仕組み。 純 MEF 2 枚で実現できる (AsyncPackage / VSCT 不要): 

[ExportLaunchDebugTarget(PROVIDER_GUID, new[] { ".nhsp" })]
internal sealed class NhspLaunchDebugTargetProvider : ILaunchDebugTargetProvider {
    public void LaunchDebugTarget(IWorkspace ws, IServiceProvider sp,
                                  DebugLaunchActionContext ctx) {
        string target = ctx.LaunchConfiguration.GetValue("target", "");
        // compile → IVsDebugger4.LaunchDebugTargets4
    }
    public bool SupportsContext(IWorkspace ws, string p) => throw new NotImplementedException();
}

[ExportLaunchConfigurationProvider(PROVIDER_GUID, new[] { ".nhsp" }, "nhsp", JsonSchema)]
internal sealed class NhspLaunchConfigurationProvider : ILaunchConfigurationProvider {
    public bool IsDebugLaunchActionSupported(DebugLaunchActionContext _) => true;
    public void CustomizeLaunchConfiguration(DebugLaunchActionContext _, IPropertySettings _) { }
}

JSON schema の "defaults": { ".nhsp": { "$ref": "#/definitions/nhsp" } } が実装の肝 — これが登録されて初めて「現在のドキュメント」エントリが dropdown に現れる。 実装: NhspWorkspaceLaunch.cs。

ShellWorkspace DLL は NuGet で復元できない

PackageReference Include="Microsoft.VisualStudio.Workspace" を追加すると NU1101: Unable to find package Microsoft.PerformanceUtilities が出る (Microsoft 内部 feed にしかない)。さらに NU1605 で Threading / Shell の downgrade 連鎖。
PTVS と同じく VS インストール先の OpenFolder ディレクトリから HintPath で直接参照する: 
<PropertyGroup>
  <NhspVsOpenFolderDir
      Condition="'$(NhspVsOpenFolderDir)' == '' AND Exists('$(ProgramFiles)\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\OpenFolder\Microsoft.VisualStudio.Workspace.dll')">
    $(ProgramFiles)\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\OpenFolder
  </NhspVsOpenFolderDir>
  <!-- Professional / Enterprise 分も同様 -->
</PropertyGroup>
<ItemGroup Condition="'$(NhspVsOpenFolderDir)' != ''">
  <Reference Include="Microsoft.VisualStudio.Workspace">
    <HintPath>$(NhspVsOpenFolderDir)\Microsoft.VisualStudio.Workspace.dll</HintPath>
    <Private>False</Private>
  </Reference>
  <!-- Workspace.Extensions / Workspace.VSIntegration も同様 -->
</ItemGroup>
$(VSINSTALLDIR) は Developer Command Prompt 以外では空なので、 SKU 順検索する条件付き property を自前で書く。

ShellWorkspace 17.12 は Threading 17.13 を要求

Workspace DLL (17.0) を HintPath 参照した瞬間に:
CS1705: Assembly 'Microsoft.VisualStudio.Workspace' uses 'Microsoft.VisualStudio.Threading, Version=17.13.0.0' which has a higher version than referenced assembly 17.0.0.0
PackageReference "Microsoft.VisualStudio.Threading" Version="17.13.2" に bump。

9. 配布用 .bat ファイル

VSIXLF-only な .bat は cmd がパースに失敗する

ダブルクリックしても何も起きない or エラーが大量に出て閉じる。 rem 行の末尾が「コマンドとして認識されていません」と言われる。

PowerShell の Out-File / Claude Code の Write tool / Node の fs.writeFileSync はデフォルト LF で書く。 cmd.exe は LF-only だと行境界を見失い、ファイル全体を 1 行の巨大コマンドとして誤認する。 

$text = [IO.File]::ReadAllText($bat)
$text = $text -replace "`r?`n", "`r`n"
[IO.File]::WriteAllText($bat, $text, [Text.Encoding]::ASCII)
メッセージは ASCII に留めるか、chcp 65001 >nul を冒頭で呼んでから UTF-8 で書く。 cmd.exe の既定コードページは日本語 Windows で CP932 なので、UTF-8 のまま出すと化ける。

VSIX自己昇格パターン

ダブルクリック 1 回で管理者昇格して同じ .bat を実行し直すパターン:

@echo off
setlocal
net session >nul 2>&1
if %errorlevel% neq 0 goto :elevate

cd /d "%~dp0"
rem ---- 管理者で実行される処理をここに ----

exit /b

:elevate
powershell -NoProfile -Command "Start-Process -FilePath '%~f0' -Verb RunAs"
exit /b

%~f0 は if (...) ブロック内でも安全に展開される (変数ではなく batch パラメータ参照のため遅延展開の影響を受けない)。 cd /d "%~dp0" を忘れない — 昇格後の cmd は C:\Windows\System32 から始まるし、スクリプトと違うドライブだと cd 単独では移動しない (/d でドライブ跨ぎを許可)。 実装例: reinstall_admin.bat

9.5 MSVC / Windows ヘッダの関連ハマり

VS 拡張直接ではないが、併設プラグイン DLL 開発中に踏んだ MSVC / Windows SDK 固有の罠。

VSIX関数宣言の直前行に日本語コメントを書くと C2062 が出る

// non-blocking 受信。... のような Japanese コメント行の直後に HSPMQTT_EXPORT int __stdcall hspmqtt_recv(...) を置くと error C2062: 型 'int' は不要です。関数が全く parse できなくなる。

原因不明 (UTF-8 エンコード + 特定の文字並びで発生)。関数シグネチャ列の直前 にコメントが来ている時だけ再現。ファイル内の他の場所では同じ日本語でも通る。

関数シグネチャ行の直前の comment は ASCII に留める。 本当に日本語 explanation を書きたければ関数先頭の { 内側に移動する。 
// BAD:  引数 / 戻り値の説明を日本語で長く書くと C2062 になる事例あり
HSPMQTT_EXPORT int __stdcall foo(...)

// GOOD:
// non-blocking recv. Returns bytes read or 0/negative.
HSPMQTT_EXPORT int __stdcall foo(...)
{
    // (日本語 OK) ここで引数の説明
}

VSIX関数名 _poll は Winsock2 の poll マクロと衝突

winsock2.h を include した DLL で HSPMQTT_EXPORT int hspmqtt_poll(...) を書くと謎の C2062 / C2059 エラーが延々出る。

winsock2.h / ws2tcpip.h のいずれかが #define poll WSAPoll (または類似) を定義しており、関数名を識別子段階で マクロ展開してしまう。他に衝突しそうな名前: send, recv, connect (これらは OS 関数なので export 名として使える形で避ける)。

Winsock 使う DLL では関数名を _recv / _send などと同じく 別名にリネームする。hspmqtt は hspmqtt_poll → hspmqtt_recv に変更。

VSIXWindows SDK 10.0.26100 の ws2tcpip.h で PIP_MSFILTER 未定義エラー

DuckDB amalgamation の duckdb.cpp をビルドすると ws2tcpip.h(756,5): error C2065: 'Filter': 定義されていない識別子です。 が 100+ 件出る。Filter は実際は SDK 関数の local variable 名で、 その上の PIP_MSFILTER の解決が出来ていない。
以下の define 一式を PreprocessorDefinitions に追加: 
WIN32_LEAN_AND_MEAN
_WIN32_WINNT=0x0A00
WINVER=0x0A00
NOMINMAX
_WIN32_WINNT が低い値のままだと ws2tcpip.h の Vista+ 限定 API がスルーされず、PIP_MSFILTER の前方宣言部分だけ がマスクされて unknown identifier 扱いになる。

9.9 HSP プラグイン .hsp モジュール側の罠 (補足)

VS 2022 拡張そのものではないが、プラグイン DLL を呼ぶ HSP 側のラッパ (common/*.as + #module でカプセル化した iron_*.hsp) で頻繁に踏むので併記。詳細は reference_hsp_module_quirks.md §24 にも記録。

HSP#cfunc / #func は global 付けないと #module 内から呼べない

.as ファイルで #cfunc foo ... と宣言し、それを #module mymod の中の #deffunc から呼ぶとコンパイルエラー: 
#初期化の変数が見つかりません(foo@mymod)
iron_toast.hsp(27) : error 2 : 構文が間違っています
--> foo@mymod arg1, arg2
foo@mymod のように @ 付きで解釈されている = 未定義識別子扱い。
#cfunc global / #func global にする: 
#uselib "hsptoast.dll"
#cfunc global hsptoast_show_info "hsptoast_show_info" str, str
#func  global hsptoast_clear     "hsptoast_clear"
#uselib 自身は scope を持たないので global 不要。 エラー文の @module_name サフィックスを見逃すと誤診しやすい (I 自身が最初「cfunc が str param を marshall できない」と誤診した例あり)。

HSP\ による行継続は HSP 構文でサポートされない

C/C++ 感覚で長い文字列連結を \ で複数行に分けると error 4: パラメーター名の記述が無効です。
HSP は \ 行継続非対応。+= で 1 行ずつ連結する: 
; BAD
_body = "{\"a\":1," + \
        "\"b\":2}"

; GOOD
_body  = "{\"a\":1,"
_body += "\"b\":2}"

HSPパラメータ名に title / body 等の組込み名を避ける

#deffunc toast str title, str body → error 30: 無効な名前がパラメーターに指定されています。 title は HSP のウィンドウタイトル設定命令なので、パラメータ名に出来ない。
_tl / _bd のようなアンダースコア接頭辞付きに改名。既知の予約済み名は line / pos / default / title / _f / _r / rank ほか多数 (メモリの reference_hsp_module_quirks.md に詳細あり)。
